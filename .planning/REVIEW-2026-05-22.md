## Executive Summary

The MVP is in good shape: auth, practice IDE, AI panel, skill tracking, and onboarding wizard all work. The main gaps are (a) three real bugs that silently produce wrong data, (b) several missing features the schema already anticipates (billing, orgs, SQL execution), and (c) a handful of backend/frontend inconsistencies that will cause user confusion at scale.

---

## 1. Bugs

### B-01 — Stale streak never resets after missed days
**File:** `backend/core/streak.py:44`, `backend/api/users.py:27`  
`maybe_backfill_streak` returns the cached `user.streak_days` immediately if it is > 0, without checking whether the streak is still valid. A user with a 10-day streak who misses 3 days will still see 10 on their dashboard indefinitely — until they make a new submission that triggers `recompute_streak`.

**Fix:** `GET /users/me` should call `recompute_streak` unconditionally (or at least once per calendar day via a flag), not just when streak is 0.

---

### B-02 — Critique tab earns no XP and doesn't update skill levels
**File:** `backend/api/practice.py:188` (`code_quality_review` endpoint)  
The "Critique" tab streams a code quality review but never calls `assess_submission`. XP and `skill_level` are only updated via `review_submission` (the "Review" tab). From the user's perspective, clicking Critique appears equivalent to clicking Review, but silently awards no XP.

**Fix:** Call `assess_submission` after `code_quality_review` completes, or surface the XP difference clearly in the UI.

---

### B-03 — `generate_solution_variant` bypasses plan-gated model routing
**File:** `backend/api/problems.py:228`  
This endpoint hardcodes `"anthropic/claude-haiku-4-5"` instead of calling `resolve_model(db, current_user)`. Pro users paying for a better model get the cheapest one here; the whole LLM routing layer (`llm/router.py`) is bypassed.

```python
# current — wrong
"model": "anthropic/claude-haiku-4-5",

# fix
model = resolve_model(db, current_user)
```

---

### B-04 — Piston timeout goes undetected in most cases
**File:** `backend/api/execute.py:47`  
`timed_out=True` is returned only on `httpx.TimeoutException` (outer HTTP client, 15 s). Piston's internal run timeout (3 s) returns HTTP 200 with `run.signal = "SIGKILL"` and `run.code = null` — this path returns `timed_out=False` and blank stdout/stderr, giving the user a silent failure with no explanation.

**Fix:** Check `run.get("signal") == "SIGKILL"` or `run.get("code") is None` in the success path and set `timed_out=True` accordingly.

---

### B-05 — `is_profile_complete` only checks `display_name`
**File:** `backend/schemas/user.py:18`  
A user who sets only their display name (via `/settings`) is considered "complete" and never shown the onboarding wizard, even if they have no `coding_experience`, `learning_goal`, or `interested_topics`. This silently produces an empty learning path with no user-facing explanation.

```python
@computed_field
@property
def is_profile_complete(self) -> bool:
    return self.display_name is not None  # too permissive
```

**Fix:** Also require at least `coding_experience` to be set.

---

### B-06 — `UserUpdate` accepts any string for `profile_level`
**File:** `backend/schemas/user.py:22`  
`PATCH /users/me` with `{"profile_level": "alien"}` succeeds. The field should validate against `Literal["kid", "student", "engineer"]` to match the model comment and frontend options.

## 2. Missing Features

### F-01 — Stripe billing (schema ready, integration absent)
`Plan.stripe_price_id`, `Subscription.stripe_sub_id`, `Subscription.cancel_at_period_end` are all defined. `resolve_model` already reads the subscription. What's missing:
- `POST /billing/checkout` — create Stripe checkout session
- `POST /billing/webhook` — handle `checkout.session.completed`, `customer.subscription.deleted`
- Enforce `llm_calls_per_month` quota (model exists, no enforcement)
- Frontend: upgrade prompt when Free plan limit is hit

---

### F-02 — SQL code execution
`execute.py` returns 422 for SQL. SQL problems exist in the DB (397 total). Users can read and submit SQL solutions but can't run them. Options: embed a lightweight SQLite runtime in Piston, or run against a sandboxed read-only schema using pg.

---

### F-03 — Organization / team features
`Organization`, `OrgMember` models are fully defined with roles, seats, invitations. Zero API endpoints exist. This is complete dead code. Either implement or drop the models to reduce confusion.

---

### F-04 — User-created problems
`Problem.source = "user"` and `Problem.created_by` exist. "Surprise Me" creates LLM-generated problems but users can't submit their own. A `POST /problems` endpoint would unlock community-contributed content.

---

### F-05 — Problem bookmarks / save for later
No way to mark a problem as "want to revisit." A lightweight `UserBookmark` table + toggle endpoint would fill this gap.

---

### F-06 — Admin panel
`User.is_admin` is defined. No admin endpoints exist for: seeding problems, reviewing usage events, toggling user plans, or viewing analytics.

---

### F-07 — "Mark as solved" without AI review
Users who verify their code locally via "Run" and are satisfied cannot complete a problem without triggering an AI review. The flow forces a review to update `solved_ids`. Adding a lightweight `POST /problems/{id}/mark-solved` that creates a submission record without an LLM call would remove this friction.

---

### F-08 — Email / push notifications
No streak-break reminders, no weekly progress digest, no "you hit level X in arrays" milestone. The usage_events and skill_snapshot data needed to drive these exists.

## 3. Enhancements

### E-01 — Dashboard makes 5 parallel API calls per load
**File:** `frontend/app/dashboard/page.tsx:44`  
`/users/me`, `/submissions/me`, `/users/me/learning-path`, `/submissions/me/problem-ids`, `/problems/facets` are all fetched on every dashboard render. A single `GET /users/me/dashboard` endpoint could return all this in one round-trip.

---

### E-02 — `fetch_ranked_candidates` runs on every request with no caching
**File:** `backend/core/learning_path.py:60`  
Fetches and sorts up to 500 problems in Python on every call to `/users/me/learning-path` and every "recommended" problems list. At scale this hits the DB heavily. Consider memoizing per-user per-session or using a short-lived Redis key.

---

### E-03 — `review_submission` duplicates the streaming pattern
**File:** `backend/api/submissions.py:97`  
The `event_generator` in `review_submission` manually accumulates tokens and calls `log_usage_event`. `practice.py` has a cleaner `_stream_with_usage_log` helper for exactly this. The two diverged and `submissions.py` version has slightly different logic (separate `log_usage_event` vs `log_stream_usage`). Unify to reduce drift.

---

### E-04 — `_RESERVED_SLUGS` is a fragile route guard
**File:** `backend/api/problems.py:26`  
Adding any new route under `/problems/` requires manually adding to `_RESERVED_SLUGS`. FastAPI already handles static-vs-dynamic route ordering — move `/{problem_id}` to be registered last and remove this set entirely.

---

### E-05 — `Submission.code` has no max-length guard
**File:** `backend/api/submissions.py`, `backend/schemas/submission.py`  
The 32 KB check exists only in `execute.py`. `POST /submissions` accepts unbounded code and stores it. A 1 MB submission would be sent to the LLM review endpoint at cost and fill the DB. Add `max_length=65536` to `SubmissionCreate.code`.

---

### E-06 — LLM prompt registry hits DB on every call
**File:** `backend/llm/registry.py`  
`load_and_render` queries the `prompt_templates` table on every LLM request. Prompts change rarely — an in-process LRU cache with a 5-minute TTL would eliminate this repeated overhead without complicating deployment.

---

### E-07 — `skill_level` JSONB has no type validation
**File:** `backend/models/users.py:33`  
`user.skill_level` is `dict` at the Python level with no validation that values are floats in [0, 1]. Corrupted entries (from a bad migration or direct DB edit) silently break the progress bars. Add a Pydantic validator in `UserOut` or a DB check constraint.

---

### E-08 — Score shown as percentage is misleading
**File:** `frontend/app/dashboard/page.tsx:218`, `frontend/app/progress/page.tsx`  
`Math.round(s.score * 100)%` displays 50%/75%/100% for the three scoring tiers. These numbers represent verdict categories, not actual percentage correctness. "50%" implies the user got half the problem right, which is untrue. Consider labels like "Needs work / Good / Correct" instead.

---

### E-09 — Practice page loads full problem list even if user never opens the list tab
**File:** `frontend/app/practice/[id]/page.tsx`  
`problemList` is fetched on mount but only rendered if user clicks the "Problems" tab in the description panel. This adds a DB query + network round-trip on every practice page load. Lazy-load on first tab click instead.

---

### E-10 — Progress page fetches learning path data it doesn't display
**File:** `frontend/app/progress/page.tsx:49`  
`/users/me/learning-path` is fetched but the Progress page only uses it to compute `solvedCount` and `totalCount`, which are also derivable from the already-fetched `solved_ids` + `submissions`. Drop this call from the progress page.

---

### E-11 — No error state if problem 404s in practice page
If a user navigates to `/practice/invalid-id`, the `problem` state stays `null` and the page renders a blank editor with no user feedback. Add an explicit "Problem not found" error state.

---

### E-12 — Learning path size is hardcoded at 15
**File:** `backend/core/learning_path.py:24`  
`PATH_SIZE = 15` is not configurable per user or experience level. A "none" experience user gets the same 15-problem path as a "professional" who only needs 5 warmup problems before hitting medium difficulty. Consider varying path size by experience.

---

### E-13 — `submission.score` description in history table
The submission history table in `progress/page.tsx` shows a score column but the `SubmissionHistoryItem` schema returns raw float scores (0.5/0.75/1.0). If a user submitted without ever requesting a review (`score = null`), the cell is blank with no explanation. Add a "No review yet" label.
